# Fleet controls: selection, command ship, ship bar and formations

Scope: UI-01, UI-02 and UI-03 in the [fidelity backlog](../fidelity-backlog.md). Sections 1–3 record original evidence; §4 preserves the pre-implementation audit, §5 the ordered acceptance checklist, and §6 records the shared implementation and checks. **Implemented provisionally, not retail-parity validated.**

## Evidence and confidence

- **Manual:** the game's `Treasure_Planet_eManual.chm`, `Play/Advanced_Controls.htm` (Ship Bar, Ship Selection, Controlling Secondary Ships, Fleet Commands, Right-Click Commands), `Play/Basic_Controls.htm`, `Standard/Options.htm` (keyboard table). Text/images are not copied into this repository.
- **Data:** converted `assets/hud/hud.json`, `content/data/hud/bar.json`, map player formation fields and Mission01–13 rule lists in `assets/maps/mission*/mission.json`. HUD has faction-specific normal/hover/pressed/disabled art, selected slots, health strips, ship icons, status art, formation buttons and offsets. These establish available presentation, not functioning remake controls. TST front-end control labels/rebinding are not battle input semantics.
- **Original game behaviour:** input handlers and command executors of the original game, described in our own words.
- **Runtime comparison:** source review, not a new runtime test. Existing local modifications were left intact. No original executable was launched, and no Steam file was changed.

**Confirmed/manual** means explicitly described by the manual. **Confirmed/static** means the behaviour was established in the original game itself, not merely from a string match. **Unknown** means not yet recovered; do not turn it into a default retail rule.

## 1. UI-01 — three distinct states

The original keeps **one selected object**, **one fleet primary/command ship**, and **one camera focus** separately. Selection is not multiselect. A secondary remains captain-controlled when selected; selection alone does not promote it.

Confirmed/static:

| State/path | Established behaviour |
|---|---|
| Selected object | Stores the object identity; notifies deselect/select observers. Focuses the camera if a HUD flag is on **or the same object is selected again**; the flag's user-facing name/default remains unknown. |
| Selected ship | The selected object, required to be a ship (object flag bit 8). This is **not** the primary. |
| Primary ship | The local player's fleet primary, independently of the selection. |
| Secondary list / eligibility | Fleet members after index 0; eligibility is membership in that list, not merely an allied relationship. |
| Camera focus (FocusOnSelected input) | Focus changes camera state; F focuses the selected ship without changing command ownership. |

### Controls and order routing

- **Manual:** mission start selects the command ship; a blue disc marks the selected ship. Left-click an own secondary in the world or its ship-bar icon to select it. The manual describes automatic camera follow on selection, the secondary's name at the top, and unavailable command-ship controls while a secondary is selected. **Static refinement:** camera follow on a new selection is conditional on a flag; repeat selection still refocuses. Whether/how that flag is exposed as a preference is unknown.
- **Primary key / bottom primary portrait:** input → primary getter → common selection setter. It selects the primary, not just the camera. Plays `HUD_SelectShip_Primary`.
- **Secondary keys:** input reads its stored zero-based slot → secondary list → common setter. Input constructors register **ten slots, 0–9**. Out-of-range slots do nothing, without the successful-selection sound. Successful indexed/bar selection plays `HUD_SelectShip_Secondary`. The bar need not be open for a number key to work.
- **Cycle next/previous:** use the complete local fleet list, **including primary**, and wrap last→first / first→last. They require the current selected object to be in that fleet; they do not repair an absent/foreign selection. Both call the common setter. No explicit selection sound in these cycle handlers (unlike primary/indexed helpers).
- **World hover/click:** a hostile hit generates primary-attack intent when selected==primary, secondary-attack intent when selection is in the secondary list. Both create `AttackShipCommand` (`0x10`) with the **selected ship's identity** and target/aim position. Executor installs its target, explicit-order stance 4 and attack task 1. A secondary captain executes the attack; it is not a direct manual weapon-bank click.
- **Manual:** a secondary can receive a destination and attack target, but not a plotted path or manually chosen speed. `MoveShipCommand` executor takes a ship identity, sets explicit-order stance 4, task 3 and a path. Its primary-specific start-speed branch tests the ship's control mode. This does not establish every world-plane input branch or arrival rule; those remain UI-04 / SIM-01 follow-up.
- **Important click distinction:** hover over the **already selected ship** produces focus-only intent `0x11`; hover over the **primary while another ship is selected** produces selection intent `0x12`; another eligible secondary produces `0x13`. Thus clicking primary returns selection to it. Focus-only actions on other objects must not redirect orders.
- Selection, cycling and ship-bar keyboard input all reject three HUD gates. Two of them also guard primary/indexed helpers. **Unknown:** complete named meaning of all gates; do not equate all three to ordinary pause. Cinematic/modal blocking must be preserved, not bypassed by hotkeys.

### Default-key evidence and conflicts

The manual keyboard table gives primary `'`, secondary 1–9, next `]`, previous `[`, ship bar S, focus-selected F and change-primary P. The executable registers ten secondary slots; the remake's retail binding table supplies 1–9 and 0 for slot 10 and uses Backquote for primary. **Unknown in this pass:** native primary-key scan-code / keyboard-layout mapping and the tenth slot's default key. Preserve that discrepancy explicitly rather than claiming the manual establishes Backquote/0. Rebinding should feed these existing `Act` rows, not another hardcoded key path.

The pre-implementation runtime hardcoded **P for pause** and **[/] for simulation speed**, colliding with advertised fleet actions. These collisions are now removed: P and brackets consume the rebindable fleet actions. Pause remains on the existing HUD button / Esc menu; speed remains on the existing 1x–16x HUD button and `--speed`. The physical **Pause key** is an explicitly **non-retail convenience**, also used by the pause smoke driver; it is not a recovered replacement retail default.

### Changing the command ship

**Confirmed/manual:** P is available in skirmish/multiplayer only, not campaign. **Confirmed/static:** `ChangePrimaryShip` input rejects a world flag (campaign), then creates `ChangePrimaryShipCommand` **id `0x1f`** containing local player index and selected ship identity. Manual restriction and branch agree; the flag's other writers were not exhaustively inventoried.

Executor checks that the selected candidate belongs to that player's fleet, then promotes it. The helper removes its existing entry, inserts it at the front, and rebuilds fleet control/notifications:

- The chosen ship becomes index 0. Other entries retain their relative order, so the old primary becomes a secondary and secondary-number indices change.
- Removal/reset clears the promoted ship's formation/related flags and hold-fire (including gun-level flags). Rebuild puts the human fleet's new first ship into direct-control mode and former primary back into AI mode; a no-longer-primary direct-controlled ship has formation flags reset by that mode change.
- Primary- and secondary-fleet-change messages are broadcast. Ship bar subscribes to both, so its membership must rebuild; HUD ownership is not inferred from camera focus.
- Executor reads the promoted ship's actual velocity magnitude and maximum-speed accessor, writes a clamped **0..1 speed fraction**, using 0 for near-zero maximum speed. It does not blindly reset a moving candidate to All Stop. Mapping that fraction to retail engine-order labels still belongs to SIM-01.
- The input leaves selection pointing at the same ship. There is no explicit camera-focus call or special promotion sound in the executor. Observer-driven HUD effects must not be confused with a guaranteed new camera jump.
- Membership excludes another player's allied ship. There is no explicit already-primary rejection: even the current primary can take the reset/reinsert path. There is no separate sight-distance, class, damage-percentage or tender ban in the traced input/executor. **Unknown:** general list maintenance/destruction checks, pending boarding/docking cancellation, and an extra removal branch gated by custom-info and crew fields; do not assert all damaged/special ships always qualify.

**Script is a separate route:** `Set Fleet Primary Ship` is `SetShipAsPrimary`. It resolves the named Group/Unit and invokes the same promotion helper; it does **not** go through the campaign-blocked P handler. Missions **5 and 9** use it, including Mission 9's `Players Ships,RLS St Roch`. The resolver/owner-transfer details for a candidate from another group are not fully recovered. Do not disable scripted changes just because user promotion is disabled in campaign.

### Selection edge cases still unknown

- Exact replacement selection/primary after destruction, loss by capture, despawn, or an empty fleet; initial no-primary flow (notably Mission 9) and which callbacks clear stale object IDs.
- Ordering after joins/capture besides the confirmed promotion reorder; how hidden/script-ineligible members enter/leave the fleet list.
- Exact per-widget secondary overlay/disabled behaviour, transition timing and off-screen selection feedback. The manual confirms restrictions, but not a complete widget inventory.
- Whether all world-click paths play the same sounds as indexed/bar selection. The common setter itself does not play those sounds.

## 2. UI-02 — secondary ship bar

**Confirmed/manual:** bottom-right toggle opens the secondary list; icons represent secondaries only. A left-side health strip runs from healthy green to damaged red; destroyed/captured ships disappear. Left-click selects/refocuses. The manual's Right-Click Commands section describes context options on world objects; right-click **bar icons** is established by the static handler below.

**Confirmed/static:**

- S input toggles `ShipBar` through **open / close**, with an open state and an animation start timestamp. They play `HUD_ShipBar_Open` / `_Close`. Native toggle button has its own widget path (`ToggleShipBarButton`), not a world click.
- `ShipBar` subscribes to primary/secondary change messages; receivers **rebuild** it from the secondary list. Population is capped at **ten secondary entries**, not ten including primary. Do not interpret this as a proven global fleet-size limit.
- Layout: two columns, final lone cell centred; available-height-dependent placement and slide offset. It lays out secondary slots independently of the bottom primary icon. Up/down art and overflow-related layout branches exist, but full scroll semantics are **unknown**; arrows alone do not prove a scrolling implementation.
- Draw: the chosen slot is identified by comparison with the selected ship; uses selected-slot background independently of hover/pressed state, type icon from custom info, vertical health clipping and per-ship status art. Health calculation sums the platform's body and section health pools, not crew count or just one sail. Exact accessor-field interpretation and colour/rounding parity need a focused damage comparison before using the remake's aggregate health as identical.
- Left press sets a cell-local pressed latch; release selects only if left release remains inside that latched cell and then clears latches. Pressing outside or dragging out must not issue a world move/selection on release.
- Right click opens/toggles the existing object options menu; not a primary promotion shortcut. Slot hit-testing is separate from selecting that ship as command owner.
- Update closes when its HUD gate or absence of a primary makes it unavailable and records a reopen flag; when the gate clears and a primary exists, reopens if it had auto-closed. Closed/animating state also controls its input window. Do not keep invisible hit rectangles active.
- Converted HUD data includes `ShipBar_*`, `Offset_ShipBar_*`, `ShipBar_ShipIcon_*`, `ShipBar_Selected_SlotBackground`; animation fields are ShipBar 2.0, toggle open/close seconds 1.0. **Data-confirmed only:** the unit/curve of the first value was not fully traced; do not treat 2.0 as seconds without checking the animation evaluator.

**Unknown:** status-icon priority when multiple relations coexist (dock, board, held position, tow), all health-strip colour thresholds, tooltip/name formatting, overflow/scroll input, and capture/hidden-member filtering before the list getter. The existing primary status path is reusable but not proof that every secondary status uses the same precedence.

## 3. UI-03 — fleet formation commands and following

### Controls, hold and feedback

**Confirmed/manual:** the bottom Fleet Commands button opens the window. Six formation buttons, left-to-right **Line Abreast, Echelon Left, Echelon Right, Column, Diamond, Convoy**. Choosing one assembles secondaries around/following the command ship; active button is yellow. Repeat click disengages. An individual secondary move order releases that ship from formation. Two more buttons order secondaries to attack the primary's target and to cease fire. Position-lock in a secondary's options menu is a separate behaviour: it may fire but does not pursue/retreat/respond to fleet commands (UI-05).

**Confirmed/static:**

- `FormationBar` press/release → click → **SetShipsFormationCommand id `0x19`**. Payload: player index, formation enum, hold boolean. Open/close use separate state/timestamps and `HUD_FormationBar_Open/Close`; click plays the sound before dispatch.
- Click a **different** type: hold=true. Click the current type: invert the all-held test, which returns whether **all secondaries** currently hold formation. If even one left, clicking that same type reassembles the fleet instead of releasing the rest. Empty/primary-only fleet returns all-held=true; repeat-click therefore sends hold=false, harmlessly with no follower loop.
- Execute: stores fleet type, recalculates layout when members exist and type is not None, then invokes the hold setter. Hold is **per secondary AI**, loop starts at index 1 and never applies it to primary. Enabling pushes task 0 before setting hold=true; disabling ends the formation routine if active. Formation type is retained when hold=false; disengaging is not equivalent to selecting None.
- Button art is active only when its type matches **and all secondaries hold**; a detached secondary removes the fleet-wide yellow indication even while others still follow. Selection alone does not clear hold.
- Move executor → task 3 → the routine resolver stops the formation routine, clears hold, returns that ship's movement routine. Other followers are untouched. Resolver also releases formation for task 4 and docking/towing/boarding tasks 6/8/7 (and 12). Attack task 2 can choose the **attack-with-formation routine** while hold is set, rather than forcing all attacks to detach. Do not collapse every explicit order into the same release rule.
- **FleetHelpCommand id `0x1a`:** click modes 0=attack primary target, 1=hold fire, 2=resume fire. Hold-fire is a separate fleet / per-ship flag plus gun flags; cease-fire button toggles mode 1/2 from current state. Attack mode propagates the primary's current target and task 2 to secondaries when a valid target exists. Targetless attack cannot invent a target. This is not hold-position and not hold-formation.
- **Mission rules:** `Set FleetFormation Type` (`SetFormationType`) resolves Player Name, type string **and Hold Formation**, recalculates the layout and calls the same hold setter. `Set Fleet Hold Formation` (`SetHoldFormation`) changes hold without changing type. These operate on the named fleet, including AI fleets, not only the human's selection.

### Layout and following recovered from code

Formation types:

| Enum | Name | Confirmed construction before assignment post-pass |
|---|---|---|
| 0 | None | No generated layout. No formation-follow eligibility (requires nonzero type). |
| 1 | Custom | Records existing member positions relative to leader; does not replace them with LineAbreast. |
| 2 | LineAbreast | Leader at origin; member i uses slot max(i−2,0), alternating port/starboard steps of R+30. |
| 3 | EchelonRight | Chain from slot i−1, starboard-axis direction rotated −35°, step R+30. |
| 4 | EchelonLeft | Mirrored +35° chain from slot i−1, step R+30. |
| 5 | Column | Chain from slot i−1 aft along leader's forward axis, step **2R+30**. |
| 6 | Diamond | Alternating signed starboard-axis steps rotated ±35°, relative to max(i−2,0), step R+30. Do not substitute a generic four-point diamond. |
| 7 | Convoy | Same alternating construction, but ±45°, step R+30. |

R is the **largest native member size field**, not an established match for our section-box radius. Geometry is planar (z component cleared); slot 0 is leader position. Angle initializers multiply π/180 by 35/45; spacing constant is 30. Direction signs here describe the original game axes (x starboard, y forward, z up), not Bevy yaw signs. Check those transforms when implementing.

The layout stores **leader-relative distance and angle**; reconstructs a slot from the leader's current pose. Thus slots rotate and translate with the leader, not fixed lateral offsets along every route point. A post-pass (except Custom and Column) swaps slot assignments using a distance/heading-cost calculation. The generated geometry is recovered, but **exact member-to-slot assignment/tie behaviour is still unknown**; do not freeze ECS iteration order as retail slot order.

`ShipMoveInFormationRoutine` update checks fleet/type/membership, gets current slot, adds a leader-velocity look-ahead, and chooses speed according to slot/heading conditions and leader/follower limits. It supplies a movement path and normalizes the desired speed against follower maximum speed. This is continuous following, not a one-off spawn arrangement or cloned group waypoints. `ShipAttackWithMoveInFormationRoutine` combines formation movement and attack handling.

**Unknown:** exact look-ahead/catch-up/heading thresholds, collision/path-planner interplay, member reassignment after casualty or primary change, whether every position-locked ship is excluded by each fleet command, and native size-field equivalence. These are calibration tasks, not a reason to implement None/Custom/Column as LineAbreast.

### Mission evidence that needs real consumers

Mission 1 requests **Diamond and Convoy with hold=true**, later None/false. Column appears in 3–5,7,10; EchelonRight in 4,11; EchelonLeft in 11; LineAbreast in 9; Custom in 5–7,11,12. Separate hold actions occur in 3,5,9,11. Mission presence does not prove a new blocker or invalidate the completed manual Mission 1 playthrough. It proves universal LineAbreast/35-unit route offsets are not the requested behaviour.

## 5. Ordered implementation / acceptance checklist

Implementation followed this order; §6 records the completed paths and explicit fallbacks. Native-key/modal/loss recovery, controller calibration and the final retail / full Mission 1 acceptance are **not** claimed completed by remake tests.

2. **Separate selected, primary and camera state in the shared model.** Preserve PlayerShip's command-owner meaning until each caller is audited; selection must not move that marker. Handle startup, empty fleet, stale/despawn/capture selections, leave/restart and mission stand-in handoff explicitly. Test that focusing an enemy never redirects a ship order or changes mission primary.

4. **UI-02 complete ship bar.** Shared open/closed/auto-hidden state and roster; classic uses existing faction art/metrics. Scenario: own command ship + ≥3 secondaries + a separately owned allied fleet + enemy; select each route, focus elsewhere, issue independent orders, promote in skirmish, rejoin all six formations, cease/resume fire, remove/capture a member, restart/re-enter. Add synthetic Mission 1 Diamond/Convoy/None and Mission 5/9 primary actions; then normal Mission 1 replay. Update UI-01/02/03 only for checks actually completed; runtime smoke/unit expectations alone are not an original-game comparison.

## 6. Shared implementation and validation record

### What landed (UI-01/02/03)

- **State and ownership first:** `ship.rs::Fleets` keeps one selection and stable ordered named rosters; `PlayerShip` remains the command/direct-control marker and `Orbit.focus` remains camera-only. `FleetMember` records skirmish player identity independently of Side; campaign membership follows `MissionShip.owner`. Selection never moves the marker. Initial selection is the primary; hidden mission members retain membership (world picking still rejects hidden objects).
- **Callers audited:** targeting/fire and destruction, camera/debug HUD, primary skin/gauges/audio, course/collision, radar/starmap/world navigation, briefing/NIS, options-menu/docking/boarding actor resolution, scenario outcome/restart/exit, campaign spawning and `Unit.primary` matching. Primary-bound consumers retain that meaning. The selection disc/name and target chevrons follow selection; objective navigation stays command-bound. Options-menu focus can look at an enemy without redirecting orders. User docking/boarding/towing messages carry the selected actor explicitly; script `None` actors still resolve the command ship.
- **Selection input:** existing Bindings drive primary, ten indexed secondaries, wrapped next/previous (including primary), F and S. Portrait, world own-fleet hit and bar selection share `Fleets::select`; repeat selection refocuses. Successful primary/indexed/bar selections use existing sounds; cycles are silent. New-selection camera follow uses the manual's default, pending recovery of the native preference flag. Existing cinematic/rule lock, in-game overlay, star-map and options-menu gates are honoured. World orders ignore UI clicks.
- **Orders:** primary retains engine orders, manual course and bank/panic controls. A secondary gets one captain destination (no Shift-plotted path or user engine order) and its own attack target. Formation move releases only that secondary; attack can retain formation. Existing skirmish/mission captain AI and combat handle attacks; no second fleet simulation was introduced. Secondary selection hides the manual weapon panel and gates both views' engine controls. Engine dial/tab input is shared in `panels.rs`; the views only tag/draw those controls. Full native per-widget overlay inventory remains unvalidated.
- **Ship bar:** one shared open flag and model, primary excluded, ten displayed secondary cells, two columns / centred final cell, independent selected/hover/press state, selected name, aggregate health and docking/boarding status. Casualty/capture/promotion rebuild membership. Left press must release over the same roster entity; dragging out or a hidden bar does not select. Right release requests the existing options menu, not promotion; its dock eligibility reuses the world picker check. The open preference survives automatic modal/no-primary hiding and reappears when available. Classic uses converted slot/icon/formation art; remaster draws the same shared state/actions.
- **Manual camera timing:** `view.rs::input` uses `Time<Real>` for keyboard rotation/zoom, keeping the existing 1x rates at every simulation speed and while paused. Mouse drag/wheel remain pixel-based; scripted NIS camera timing remains simulation-driven. Regression runs the actual input system at 1/2/4/8/16x and paused with identical yaw/zoom changes. Gate: 195 Rust / 74 Python tests, seven skips; Classic 16x startup smoke `local/camera-realtime-16x.png`. Interactive feel still needs owner confirmation.
- **Promotion:** eligible living own members only for P, never merely same-side allies; P is disabled in campaign but `Fx::Primary` dispatch is not. Promotion moves the candidate to index 0 while retaining other relative order, swaps manual/AI roles, resets candidate hold/hold-fire, keeps selection on it and does not move the camera. A continuous 0..1 command fraction preserves the candidate's speed; this is separate from `Ship.cap` (mission throttle limit), and later manual engine orders replace the fraction. Primary-bound HUD/rule consumers see the new marker. Script handoff removes an obsolete stand-in command ship.
- **Formations:** all eight names have real consumers; six buttons are in manual order. None disables following; disengaging retains the type. Custom captures current leader-relative positions; generated layouts implement the recovered chains, ±35°/±45° and R+30 / 2R+30 spacing. Map spawn uses its formation enum instead of universal LineAbreast. Named-fleet type and separate hold rule actions work for AI fleets too. Group paths no longer use the fixed 35-unit offset stand-in: held followers continuously reconstruct their slots from the current leader pose.
- **Per-member following and commands:** hold belongs only to followers. A matching button releases only if all secondaries hold; a partial fleet reassembles. Yellow feedback likewise requires matching type/all-held. Busy docking/towing/grappling/boarding actors detach without releasing siblings; those routines retain movement ownership. Fleet attack copies only a valid primary target and can attack while following; targetless attack is a no-op. Cease/resume fire affects secondaries, not primary, and is not formation or position lock. UI-05's position-lock placeholder is unchanged.
- **Lifecycle:** reconcile removes dead/despawned/transferred members, stale selections and invalid captain targets; stale destroyed/despawned camera focus clears. Restart and battle exit reset fleet/UI/target/focus state; the next scenario selects its new command ship. Capture transfers skirmish FleetMember ownership as well as side, and mission owner remains authoritative.

### Explicit provisional fallbacks / remaining work

1. Backquote / 0 stay the existing rebindable defaults; the manual's apostrophe and the native tenth-slot default remain unresolved. Camera follow is always on for a new valid selection; no speculative preference/rebinding framework was added. Existing named modal gates are used, not a guessed mapping of all three native gates.
2. On primary loss, choose the first living remaining own member as command ship; an empty fleet has no marker/selection and loses a skirmish. Captures/joins start detached and inherit the fleet cease-fire flag. Hidden members retain roster membership. These are safe remake lifecycle policies, **not recovered native replacement/filtering rules**.
3. Cross-group scripted promotion explicitly transfers the candidate into the local owner fleet; other source-group members remain there. Synthetic Mission 5/9 dispatch and stand-in retirement work, but general native resolver/transfer semantics remain unknown. Existing docking/boarding relations are retained during promotion (busy routines still own movement); native cancellation semantics need recovery.
4. Native size/accessor equivalence, optimal member-to-slot assignment, casualty/custom-slot reassignment and tie policy are not recovered.
